Follow CLAUDE.md §0, then §4.7. Mode: $ARGUMENTS

Without `--apply`:
1. Run the `/tos-lint` procedure (script + agent pass), keeping its findings for step 3.
2. Gather from `wiki/`: the active project portfolio (`status` not `deprecated`, `stage` not `paused` or `done`) in `priority` order, unranked last, and for each one this week's movement drafted from the week's `log.md` entries that link it, the Source pages that link it, and `git -C <data.root> log -p --since='7 days ago' -- <path>` — qualitative only, no unattested numbers; pages ingested in the last 7 days (from `log.md`); the verify queue (top `review.verify_queue` unverified or changed-since-verified pages, ranked as in `/tos-verify --queue`, **excluding active Projects** — they are verified from their portfolio rows; paused and done ones still queue); the re-pull queue (source drift); pages stale or expiring within `review.expiring_days` (**excluding active Projects** — an expiring one shows in its row); `next_checkpoint` dates in the past (**excluding active Projects** — likewise); RFCs with `status: draft`; System pages expiring within 14 days or with unticked standards; open Question pages.
3. Write `wiki/reviews/<ISO-week, e.g. 2026-W36>.md` from `schema/templates/review.md` with `generated: { by: process:weekly-review, at: now }` and these H1 sections, each a checklist the human can answer inline with `→ <answer>`: **Projects — ranked portfolio** · Ingested this week · Verify queue · Re-pull queue · Expiring (refresh / extend / deprecate) · Checkpoints passed (initiatives) · Design — awaiting your decision · Systems · Questions · Lint · Engine proposals. Phase 3+ sections (Comms due, 1:1 prep) only when the phase allows.
3a. *Projects — ranked portfolio* is the first section and reads as the summary the human talks to their manager, the Product Trio and other tech leads from. One `## <n>. [Title](path) — <lead|support> · <stage> · <trust tier, date>` per active project in priority order, annotated `(▲ from 3)` / `(▼ from 1)` / `(new)` against last week's Review page, plus `checkpoint YYYY-MM-DD passed` and `expires YYYY-MM-DD` when either applies; then the drafted entry as bold-label bullets (**Progress** · **Challenges & risks** · **Blockers & support needed**, naming who the support is needed from · **Open questions & decisions** · **Notes**), omitting labels with nothing to say and saying "no recorded movement this week" when the week was silent; then an answer line `→ `. Say under the heading that **an unanswered row means: entry accepted, rank kept, no verify** — running `--apply` is the consent. The verbs, comma-combinable on one line: `rank <n>` · `entry: accept | skip` (or edit the bullets in place) · `fix: <text>` · `role <lead|support>` · `stage <value>` · `checkpoint <YYYY-MM-DD>|clear` · `objective: <relative path>` · `support: <text>` · `extend | deprecate` · `verify`. List paused projects unranked after the ranked rows, each accepting `stage <value>` (the un-pause path) or `deprecate`.
4. Add the page to `reviews/index.md`, log `* **Review**: [Week NN](reviews/<file>) written`, commit. Tell the human it is ready and how to answer (edit the page inline, then `/tos-weekly --apply`).

With `--apply`:
1. Read this week's Review page and every `→` answer. If it is already `status: stable` it has been applied: say so and stop unless the human asks for a re-run. `--apply` is otherwise safe to retry after a partial failure, but retry it **per action, not per row**: a row may have appended its entry and got no further. For each action separately — the `## <ISO-week>` heading in the project's *Weekly log*, the live-section edits it implies, each frontmatter field the answer sets, the row's log line under today's date, the verification — check whether that one already landed, redo only the ones that did not, and finish the row. Never write a second entry for the same week, and never take a present heading as proof the rest of the row was done.
2. Execute each. `entry: skip` on a row means the week is not worth recording: write no entry and make no live-section edit for it, however much the agent drafted, and still apply that row's other answers. Otherwise a *Projects* row **that records movement** — bullets the agent drafted, bullets the human edited or added, or a `support:`/`fix:` answer that supplies content — → append its entry as `## <ISO-week>` at the top of the page's *Weekly log*, with `generated: { by: process:weekly-review, at: now }`; carry the entry into *Status*, *Next*, *Risks* and *Decisions* — add what it reports and strike only what it explicitly resolves or supersedes, never adding anything the human did not see in the row, and never dropping a live item because this week's entry was silent about it; apply `role`, `stage` and `checkpoint` edits; `objective:` → add the link under *Expected impact*; `support:` → write it into the entry's **Blockers & support needed** bullet before appending; update `stale_after`; log `* **Review**: [Title](path) — weekly entry <ISO-week>, priority N`. A row that records no movement writes **nothing at all** — the gap in the log is the record of a quiet week, and the page keeps its verification. The control answers (`rank`, `role`, `stage`, `checkpoint`, `objective:`, `extend`, `deprecate`, `verify`) do their own work on their own; none of them is movement, so none of them creates an entry — ranking or verifying a quiet project must not invent a week of progress. `fix: <text>` → make the change and log `* **Ingest**: [Title](path) — revised after review`. Any transition out of active (`stage paused`, `stage done`, `deprecate`) also removes `priority`. `verify` → run the `/tos-verify` procedure for that page **last**, so the verification covers the entry just written. Then the other sections: `extend` → move `stale_after` by the type's horizon and log `Verify` only if the human also said verify, otherwise log `Ingest`; `deprecate` → `status: deprecated` with the reason, log `Deprecate`; `refresh`/`re-pull` → run `/tos-pull` on the page's pointer; a verify answer → run the `/tos-verify` procedure for that page; a question answer → update the Question page's *Resolution*; a checkpoint answer → update `next_checkpoint`.
2a. After every row: renumber `priority` 1..N contiguous across the active projects — answered ranks win (ties broken by last week's priority), unanswered rows keep their relative order in the gaps, and an active project with no priority takes a tail position in listed order. Rewrite the `## Pages` list of `delivery/projects/index.md` in that order, then paused, then done, leaving deprecated pages under `## Deprecated`. Log `* **Review**: priorities — 1. [A](…), 2. [B](…) (was …)`.
3. Engine proposals the human accepted: apply them in this engine repository, add a line to `CHANGELOG.md`, commit the engine — and write nothing about it in `wiki/log.md`. If an accepted proposal changes existing data pages, log that change as `* **Migration**: … (engine <version>)`.
4. Mark the Review page `status: stable`, log `* **Review**: [Week NN](reviews/<file>) applied — N actions`, commit.

0 · In one screen

What this is

You curate sources and ask questions; the agent does the bookkeeping. That is Karpathy's division of labour, and it is what lets a knowledge base survive a busy quarter. The catch with an agent-written wiki is trust: after three months you cannot tell which pages a person checked, which are guesses, and which quietly expired. OKF v0.2 answers exactly that, with five frontmatter fields and one page type for numbers.

So the system is small: an engine of instructions and scripts, a data root of markdown fed through read-only connectors, one config file joining them, one page contract, twenty page types, eleven operations, a weekly tick and a sprint tick. Karpathy supplies the loop and the habit of reading the index first; OKF supplies the trust signals and the reserved shapes that make a bundle conformant. The Level 5 role description supplies the weights: which types exist, which pages must be human-reviewed before anything is built on them, and what Monday asks you.

1 · Architecture

Two trees, one bundle, two actors

Engine and data are separate trees

Karpathy's three layers are raw, wiki and schema. The first two are data: they are about your work, they contain company material, they grow every day. The third is machinery: it says how the agent behaves, contains nothing about your company, and changes when you change your mind about the method. So they are two repositories. The engine holds CLAUDE.md, the commands, the type registry, the templates and the scripts; you could publish it, or hand it to a colleague to run over their own data. The data root holds raw/, wiki/ and the Obsidian vault files, privately, in company-approved storage. A config file, one per installation and never committed, joins them.

The two trees

The OKF bundle root is wiki/, not the data root: that keeps raw/ — notes, pins and metric snapshots, none of which carry a type — out of the conformance rule, and lets team/playbooks/ be lifted out later as a bundle of its own. Obsidian opens the data root as its vault; Claude Code runs in the engine and is granted the data root as an additional working directory.

The config file

One file per installation, in YAML, outside both repositories at ~/.config/tos/config.yaml. It names the data root, the rollout phase, each connector's provider and scope, the feeds allowed to run unattended, and the review thresholds. It holds no credentials: connector auth belongs to the MCP server configuration, and the one script that could ever need a token is given the name of an environment variable. The engine never writes this file. If it is missing or unreadable, every operation stops and says so; if it names a data root that does not exist, every operation except /tos-init — whose job is to create that root — does the same.

~/.config/tos/config.yaml
engine: "0.10"                          # version this config was written for; drift is reported, not enforced
data:
  root: ~/work/tos-data                  # raw/, wiki/, Home.md, .obsidian/ live here
  timezone: Australia/Melbourne          # every date the engine writes comes from here, not the host
  actor: human:rafael                    # the human actor in every verified entry
rollout:
  phase: 1                               # 1 documents · 2 Jira + sprint · 3 team + Slack · 4 vision + radar
connectors:
  confluence: { provider: mcp:atlassian, scope: { spaces: ["ENG", "PDLC"] } }
  gdocs:      { provider: mcp:google-drive }                                         # no scope: any Doc your account can open
  md:         { provider: filesystem, scope: { repos: ["~/code/asset-search"] } }
  web:        { provider: mcp:fetch }
  jira:       { provider: mcp:atlassian, scope: { projects: [], boards: [] } }      # phase 2
  slack:      { provider: mcp:slack, scope: { channels: [], dms: false } }          # phase 3
feeds: {}                              # the only pulls that run without a pointer; none in phase 1
review:
  weekly_day: monday
  verify_queue: 5                        # how many pages Monday may ask you to verify
  draft_age_days: 14                     # lint flags drafts older than this
  expiring_days: 7                       # lint flags pages expiring within this window
  weekly_log_grace_days: 16              # an active project silent longer than this is a finding

Two logs, one rule

wiki/log.md records changes to the data and nothing else: pulls, ingests, filed answers, briefs, measurements, lint fixes, verifications, reviews, deprecations. Engine changes — a new type, a reworded guardrail, a rewritten command — go to the engine's CHANGELOG.md. The one crossing is a migration: when an engine change forces a change to the data, that is a data change, logged as Migration with the engine version.

You point, the agent fetches — and keeps your reading, not the source

A pointer is a Confluence page, a Google Doc, a repository path, a web URL, and from later phases a JQL query or a Slack permalink — given in chat or listed in raw/inbox/pull.md. Nothing is crawled on the agent's initiative; a short list of named feeds in the config may run on a schedule as process:* actors. Fetching is cheap, so the discipline matters: a channel digest is one source, not two hundred messages, and index-first navigation only holds if the wiki grows at the pace of your curation.

What lands in the wiki is your reading of a source — a Source page with a summary, the load-bearing lines quoted as short excerpts so the page carries its own evidence, and an OKF sources entry pointing back at the original with its own modified time or version. Copying the source instead would put verbatim company material, and remarks people make in Slack, into a local git history forever, for the sake of a re-read the connector can do on demand. The data root keeps verbatim material in exactly three cases: your own notes; a copy you explicitly pin, because the source may vanish or a decision rests on its wording at a date; and the query snapshots an attested number must be reproducible over. Two consequences: drift is measured against the recorded last_modified, and a Source page for a thread since deleted is exactly as good as its excerpts — which is why they are quoted.

Every directory under wiki/ carries its own index.md in OKF's list form, and the agent navigates top-down: root index → directory index → candidate frontmatter → only then bodies. A page that is not indexed does not exist.

2 · The page contract

Every page says who wrote it, who checked it, and when it expires

OKF requires one field, type. TechLead OS requires the full v0.2 trust family on top of it, because the agent writes most pages and you need to filter by tier at a glance:

wiki/systems/asset-search.md
---
type: System                           # OKF: required; from schema/types.md
title: Asset search
description: The search service behind marketplace browse.
resource: https://github.com/example-org/asset-search
tags: [system, search, owned]
owner: human:rafael                    # extension field — owner of record
sources:                               # OKF v0.2 provenance family
  - id: ops-review-2026-08
    resource: ../../raw/notes/2026-08-21-asset-search-ops-review.md
    title: Asset search — operational review, August
    author: human:rafael
  - id: incident-2026-07-30
    resource: https://example.atlassian.net/wiki/spaces/ENG/pages/9128/Incident+report
    title: Incident report — search latency
    last_modified: 2026-07-31T09:00:00+10:00   # drift is measured against this
generated: { by: claude-code/claude-opus-5, at: 2026-08-25T09:12:00+10:00 }
verified:
  - { by: human:rafael, at: 2026-08-26T08:40:00+10:00 }
status: stable                         # draft | stable | deprecated — always explicit
stale_after: 2026-11-25                # generated.at + the type's horizon (System: 90 d)
---
# Operational standards
- [x] On-call rota and escalation path documented[^ops-review-2026-08]
- [ ] Alert budget within target — breached 2026-07-30[^incident-2026-07-30]

[^ops-review-2026-08]: Asset search — operational review, August
[^incident-2026-07-30]: Incident report — search latency

Two properties of that block are contract rather than convention. It must parse: frontmatter is read with a real YAML parser and anything malformed is a conformance error that fails the lint run — tags: [a, b does not quietly lose a line. And a value that looks like a comment is one: slack: #team-search parses to nothing, which is why every pointer field in §3 is written quoted.

Trust tiers, and what moves a page between them

  • The writer never verifies. Ingest sets generated and nothing else. machine-confirmed comes from a separate pass (process:cross-check) that re-fetches the source and judges whether the page is still faithful to it. human-reviewed comes only from you. The rule is enforced, not instructed: every verified entry is appended by one script, which refuses the agent's own actor outright and refuses a human: actor unless the verify command passes --human-confirmed. The middle tier is empty today — the script accepts process:*, but the cross-check pass is not built (§9).
  • Verification is dated. If generated.at is later than the newest verified[].at, the page is reported as changed since verification and answers treat it as unverified again.
  • Status is explicit. OKF treats a missing status as stable, so an agent-written page always writes draft until it earns the gate in §3. deprecated replaces deletion: the page stays, says what superseded it, and drops out of answers unless asked for.

Freshness, and numbers

stale_after is an absolute date, computed at write time from the type's horizon: a Signal expires in a month, a System's ownership review in a quarter, a Concept in a year. Staleness is orthogonal to trust — a human-reviewed Project still goes stale after thirty days of silence, which is the point. When a page expires the weekly review asks for one of three answers: refresh, extend or deprecate. Active Projects are the exception: they expire constantly, so their expiry is reported in the portfolio row you read every Monday rather than in a queue you would learn to skip, and their silence is measured separately by weekly_log_grace_days.

A number is different from a claim. An LLM that "remembers" last sprint's completion rate is what OKF's Attested Computation type exists to prevent: the page binds a sanctioned computation to declared parameters, an executor that returns a receipt, and a deterministic attester that confirms the computation which ran is the one bound to the page. The agent supplies parameter values and nothing else. The fetch and the compute are deliberately split — the feed writes query results to an immutable snapshot under raw/metrics/, and the computation runs over that file — so the receipt can carry the hash of both, and a failing attestation is refused rather than footnoted. A number appears in a review or a brief with its receipt, or it does not appear.

Actors and timestamps

OKF's three actor forms, verbatim: human:rafael; claude-code/<model-id>, filled in with the model actually running; process:okf-lint, process:cross-check, process:weekly-review, process:pull-<feed> for scripted passes. Timestamps are ISO-8601 with the offset of data.timezone — from the config, never the host clock, or a runner in UTC stamps the wrong offset and counts a horizon from the wrong calendar day.

Extension fields, and the four that say where the work lives

Everything the registry adds to OKF is an ordinary frontmatter key — owner, role, stage, priority, next_checkpoint, level, team, quarter, superseded_by, audience, review_due, pinned, and the four pointers slack, jira, confluence, rfc. OKF consumers must tolerate unknown keys, so the bundle stays conformant and Dataview can query them directly. Relationships stay as links in the body: links are untyped, and the sentence says what kind of link it is. The exception is Attested Computation, whose fields are OKF's own and are used as specified.

A Project or Initiative may name where its work lives — the channel, the epic, the page, the RFC — one canonical pointer each, further ones body links. Four rules keep that cheap. Never required: the check reports shape and only when the key is present, so no page is non-conformant for lacking one. Shipped commented out, so a new page carries no live placeholder. Quoted, or absent — # starts a YAML comment. And a pointer is not a link: a relative rfc resolves like a body link but is deliberately not counted as an inbound one, because the orphan check exists to make you link the page from a section a reader passes through. Recording where work lives is also not reading it: a slack pointer is legal in phase 1, while only the pull command obeys a connector's phase and scope.

The writes a script owns

An operation is a procedure the agent follows; a write is a line of text with an exact shape — a log bullet, an index entry, a page's opening frontmatter, a verified entry. A canonical format re-derived from prose on every run is not canonical, it is a strong tendency, and the failures are quiet: a log bullet grep no longer matches, an index entry without its description, a horizon counted from the wrong calendar day. So each of those writes is a script, and the command files call it rather than describe it.

ScriptOwns
uv run configResolving and printing the config: paths, actor, timezone, phase. Every other script starts here.
uv run initThe data root: layout, every directory's index.md, the bundle root's okf_version, the vault files, the first log entry, git init.
uv run newA page from its template, with generated, status: draft and stale_after computed from the registry — and its index entry.
uv run logOne bullet in wiki/log.md, under today's date, newest first, with a label from the fixed set.
uv run indexAdding or refreshing a page's line in its directory index, in place, so re-indexing cannot re-rank the priority-ordered portfolio.
uv run verify-markAppending a verified entry, with the gates: the agent refused outright, human: only with --human-confirmed, process:* accepted.
uv run lintThe deterministic half of lint, and --fix.
uv run doctorThe onboarding checklist: config, layout, engine drift, vault files, git, and the config's connector names against the MCP servers actually installed.

Three properties are deliberate. They edit frontmatter at the text level and never round-trip it through a YAML writer, so template comments, key order and the flow-style generated survive. Every date comes from data.timezone. And every page operand is bundle-relative and refused if it resolves outside wiki/, so a data operation cannot write to the engine. The rule that follows: CLAUDE.md gets shorter with each release, because each script removes a procedure from prose.

Capture: pull, then ingest

A pull checks the pointer against the connector's phase and, where it has one, its scope — web and Google Docs have none, so a Doc is readable whenever your account can open it — fetches read-only, and hands what it read to ingest, keeping nothing else unless you asked for a pin or the feed is a metric feed. Ingest writes or updates the Source page, then extracts what the registry recognises — concepts, project and initiative updates, objectives, RFCs and decisions, system facts, questions — creating or updating five to fifteen pages. Three rules make it safe to run unattended: every new claim is footnoted to a sources[].id; a contradiction with an existing page goes into that page's Open questions rather than overwriting it; and an internal update goes into an existing page's timeline, never a new page — on a Project that means Status, Next, Risks or Decisions, never its Weekly log, which only the Monday tick writes. Then the indexes, the log bullets, the note moved from inbox/ to notes/, and one commit whose message is the log line.

Query

Read wiki/index.md, then the directory indexes, then candidate frontmatter, then bodies — never the whole bundle. Answer with links to the pages used and, per page, its tier and age: "human-reviewed 2026-08-26", "unverified, written by the agent 2026-08-25", "stale since 2026-08-01". Deprecated pages are excluded unless asked for. If the answer is reusable — a comparison, an analysis, a position — it is filed back as a Synthesis in draft, which is how the wiki learns from being asked.

Lint

The script pass is deterministic and reports in named groups: conformance (frontmatter parses, type present — the only findings that fail the exit code) · trust · registry (a known type, in the directory the registry gives it) · headings (the type's required headings, in template order) · provenance · stale · expiring · changed-since-verified · old-drafts · rfcs-stuck · systems (unticked standards) · projects (role, stage, colliding or non-contiguous priorities, and the weekly log's shape, repeats, future dates, order and currency) · pointers · objectives (fields, and a nudge when a lead project links no live objective, or a team objective links no company objective from its own quarter) · links · orphans · index · log.

--fix repairs only what is mechanical — a missing index entry, a dead index line, a moved or leading-slash link — in the page body, never inside a code span or a fenced block, because a markdown-shaped frontmatter value is metadata and a link in a fenced example is an example. The agent pass does what no script can: contradictions between pages, claims without a source, missing cross-references, gaps worth a Question, the people policy (§8), and source drift — for each Source page whose pointer is a connector URL in scope, compare the recorded last_modified with the live one, which becomes Monday's re-pull queue. Lint adds no verified entries in any tier.

Verify — the one write the agent never initiates

Show the diff since the last verification. On your explicit yes, the entry is appended and draft → stable only if the type's gate allows; on no, you say what is wrong, the agent fixes it, and the page stays draft. Promoting an RFC also makes it a record — its horizon runs "30 d while draft, then —", so keeping the draft's expiry would report the newly stable page as stale a month later.

The Monday tick

The weekly review runs lint, then writes a Review page that opens with Projects — ranked portfolio: every active project in priority order with its role, stage, trust tier, rank movement since last week, and the week's entry drafted from the log, the week's sources and the page's git history — qualitative only, no unattested numbers. Below it come the queues: ingested this week, the verify queue, the re-pull queue, expiries, checkpoints, RFCs awaiting a decision, systems due, questions, lint findings and engine proposals. Active Projects appear in none of those queues; they are handled, including re-verified, in their rows.

You answer inline, and an unanswered row means: entry accepted, rank kept, no verify. --apply then executes the answers, and is safe to re-run after a partial failure — per action, not per row. A row that records movement appends its ## <ISO-week> entry to the project's Weekly log and carries it into the live sections, adding what it reports and striking only what it resolves. A row with no movement writes nothing at all: the gap is the record of a quiet week, and the page keeps its verification — ranking or re-pointing a project is not movement. Then priorities are renumbered 1..N, the projects index is reordered to match, each action gets its own log bullet, and the data root is committed. Engine proposals you accepted are applied in the engine repository and recorded in its changelog, with nothing about them in the data log.

Designed, not yet running

/tos-measure and /tos-sprint (phase 2), /tos-brief (phase 3) and /tos-retro (phase 4) are specified in §9 and refused by their command files until the config allows them. One more is owed regardless of phase: the cross-check pass, which re-fetches each Source page's pointer, judges faithfulness and writes the process:cross-check entry the verify script already accepts, or reports drift. Until it exists, the middle tier of Fig. 3 is theory.

7 · Tooling

Obsidian reads, Claude Code writes, git remembers

Obsidian

Open the data root as the vault — Home.md and .obsidian/ are installed by /tos-init and are engine-owned, excluded from lint and from the log. Wikilinks off, new links relative, so Obsidian's graph and OKF consumers see the same edges. Attachments default to raw/assets/, keeping images in the immutable layer. The Web Clipper writes into raw/inbox/, so a clip is a pin. Dataview powers the dashboard: the ranked portfolio, the quarter's objectives, the unverified backlog, pages changed since verification, expiries, quiet drafts, passed checkpoints, open questions.

Home.md — the unverified backlog, newest first
```dataview
TABLE type, status, generated.at AS written, stale_after
FROM "wiki"
WHERE type AND !verified AND type != "Review"
  AND !(type = "Project" AND status != "deprecated" AND stage != "paused" AND stage != "done")
SORT generated.at DESC
LIMIT 10
```

The leading type AND is not decoration. WHERE !verified alone is true of a file with no frontmatter, so the table fills with the bundle's own index.md and log.md. The second line keeps active Projects out, since they are verified from their portfolio row instead. A query that silently matches the wrong thing is the dashboard equivalent of a check that never fires.

Connectors, and why read-only is not an instruction

One MCP connector per source — Confluence and Jira through Atlassian, Google Drive, Slack, web fetch — with read-only scopes wherever the connector offers them; markdown docs need no connector, being files at a commit. Only three things touch them: pull, the cross-check pass and the drift check. Query, brief and measure work from raw/ and wiki/ alone, so a connector outage degrades capture and confirmation, never the wiki.

.claude/settings.json denies the write-capable tools of the Google Drive, Slack and Atlassian servers — create, update, copy, share, trash, post, comment, react, transition, delete. Claude Code refuses those calls outright, so guardrail 11 does not rest on the agent declining a source that asks for a write. Reads are untouched.

Verify the deny list against your own install

A permission rule matches a tool by its exact name, and an MCP tool is mcp__<server>__<tool> where the server part is whatever you called that server. An entry naming a server you do not have matches nothing, raises no error, and appears to work. That is not hypothetical: an early list guarded two Atlassian server names that no install had, so sixteen rules were inert and silent. Hence the shape of the list today — nine server names across three connectors, breadth being cheap where a gap is not; a test that every entry is well-formed, unique and names a documented server; and a README that says which names were observed on a live install and which are inferred from the server's vocabulary. No test can reach a live MCP server, so after wiring a connector, ask Claude Code which tools it exposes and add what is missing. An enforcement mechanism you have not verified is a comfort, not a control.

Claude Code and the package

  • Run it in the engine folder, where CLAUDE.md loads, with the data root granted as an additional working directory. /tos-init is the only command that creates it.
  • uv sync installs the engine and puts its executables on uv run: config, init, lint, new, log, index, verify-mark, doctor. They are bare verbs because the tos- prefix now means one thing only — a Claude Code slash command — so they are always written as uv run <name>, which is what makes them self-identifying.
  • CLAUDE.md is the schema, loaded every run: read the config first; the two trees; the page contract; a pointer to schema/types.md; the operations as step lists; the guardrails; the read-order rule; the conventions for slugs, links, timestamps and actors.
  • schema/ holds the registry, one template per type, eleven worked examples and the vault defaults, so a new page is a copy plus content rather than a re-derivation.
  • tests/ guards what prose cannot: that malformed frontmatter is reported rather than dropped; that every shipped template and example passes lint; that init → lint works end to end; that each helper writes its canonical shape; that every deny entry is well-formed; and that a command the README gates by phase actually refuses below it, naming the same number in both places.
  • git, twice: the data root is a private repository with one commit per operation, the message being the log line; the engine is a second repository whose commits are its changelog. Neither ever contains the other.

8 · Guardrails

What the agent never does

These are CLAUDE.md §5 as it reads today. Each closes one specific failure.

  1. Never edit or delete anything under raw/. You add to it three ways only: moving a note from inbox/ to notes/ after ingest, writing a pinned copy on request, writing a metric snapshot for a feed. Each file is immutable once written.
  2. Never write a verified entry with a human: actor except inside /tos-verify on the human's explicit instruction; never any verified entry during ingest.
  3. Always write status explicitly; new pages are draft; stable only when the type's gate is met.
  4. Never delete a page: status: deprecated, say what superseded it, keep it indexed under a Deprecated heading.
  5. Every factual claim on a Concept, Synthesis, Decision, RFC, Initiative, Objective or System page carries a footnote to a sources[].id; a claim without one is an Open question.
  6. Every answer names its pages with tier and date; stale pages are called out; nothing from deprecated pages unless asked.
  7. A brief draws only on human-reviewed, fresh pages. A number comes from an attested computation's receipt or it is not a number.
  8. Update generated on every meaningful change, and the directory's index.md and root log.md in the same operation.
  9. Read index.md first, frontmatter second, bodies last.
  10. Propose engine changes in the weekly review; change the engine only when the human accepts, and record it in CHANGELOG.md.
  11. Connectors are read-only and used only by pull, the cross-check pass and the drift check. Never post, comment, react, transition or edit in any connected system — and the harness denies those tools, so this is enforced rather than promised.
  12. Pull only what the human pointed at or a named feed in the config; never DMs; never outside the config's scope. Nothing verbatim unless pinned or needed for a receipt.
  13. Never write the config file. Never write to the engine during a data operation.
  14. wiki/log.md records data changes only. An engine change is never a log entry; a data migration caused by one is, labelled Migration with the engine version.

Three of these are structural rather than advisory: 11 by the deny list, 2 by the verify script refusing the agent's own actor and refusing human: without the command's flag, 13 by every helper refusing a path that resolves outside wiki/. The other eleven are instructions, and worth re-reading as such.

People and stakeholders — the policy that matters most

A Person page contains only what your own notes state: role, the growth focus you agreed, the ownership you delegated, actions, and the thread of what was discussed. The agent never infers traits, motivations or performance, and never records health, personal circumstances, compensation or ratings, even if a note mentions them in passing — those stay in the systems built for them. A Stakeholder page is narrower still: role, what they need from the team, stated positions on live initiatives, when you last spoke. Every page about a person is human-reviewed before anything is prepared from it, and a 1:1 or a brief never rests on a draft. Slack is where remarks about people appear, which is why it is connected last, from named channels only, never DMs. Because nothing is copied verbatim, the vault holds your reading of a thread rather than the thread — but it does hold summaries and short excerpts of company material, so confirm your company's policy on that before phase 1, not phase 3. If a sub-bundle is ever exported, team/people/ and team/stakeholders/ are excluded by default.

9 · State and roadmap

What runs, and what is next

rollout.phase in the config is the switch: below its phase a command refuses and says which number would enable it, and a connector outside the phase is not fetched. Each phase adds one rhythm, in the order the role's load demands.

Phase 1
runs

Delivery, design and systems, from documents. The eleven phase-1 types fed by Confluence, Google Docs, markdown repositories and the web; daily pull and ingest; query instead of search; lint with the drift check; the Monday tick with its ranked portfolio. The engine that carries it: the config layer, uv run init, uv run lint with eighteen check groups and --fix, the four write helpers, uv run doctor, a pytest suite, and a harness deny list over the connectors' write tools.

Phase 2
next

Jira and the sprint tick. The Jira connector; the sprint-report feed writing JSON snapshots to raw/metrics/jira/; two Attested Computation pages over them; the executor, the attester and one script per metric under src/tos/metrics/; then /tos-measure and /tos-sprint. The first task is not code: capture one real query result through the connector, because the snapshot schema and the attester cannot be designed before that. Objective pages already exist for the sprint goals to point at. Goal: a sprint review whose numbers carry receipts.

Phase 3
after

Team and stakeholders, then Slack. Person, Stakeholder and Playbook pages under the §8 policy; /tos-brief and the comms-due and 1:1 sections of the weekly; the Slack connector with its named channels; the people policy as a check in lint's agent pass; and a bundle exporter that lifts team/playbooks/ out as a conformant OKF bundle of its own. Goal: Monday 1:1 prep in two minutes, and the first brief sent from the wiki.

Phase 4
later

Vision, learning, radar. Vision pages per area of influence with the signals they watch; Learning Paths, yours and a report's mentoring plan; Drills scheduled by review_due; the radar overview; Trello, a personal board, if still wanted; and the quarterly /tos-retro. Goal: a vision you can socialise from a brief, with its evidence attached.

No phase

The cross-check pass, which produces the machine-confirmed tier and waits on nothing but the work. Also unphased: a migration helper for engine changes that touch existing pages, a pre-commit lint hook for the data repository, and the test suite in CI.

Later

Extensions. Packaging as a Claude Code plugin so a colleague installs the engine rather than clones it; attested computations for system health — alert budgets, SLOs; local search once a directory index passes roughly 150 entries or a query keeps reading more than twenty bodies.

How you will know it works: most of Monday's preparation comes off the review page; every owned system has been human-reviewed this quarter; the sprint review's numbers are attested; no stakeholder update is overdue; the verify queue is never more than five; and the engine's changelog has entries, because an engine that never changed is one nobody used.

10 · Decisions

The calls this design rests on

Each of these was a real fork, and each is settled. They are here because the reason is worth more than the rule: when something in the system looks arbitrary, the answer is usually in this table.

The callWhy
Relative markdown links, never wikilinks, never leading-slash pathsPortable and conformant, and Obsidian's graph agrees with an OKF consumer. Leading-slash paths would resolve against the vault root rather than wiki/.
OKF's log.md shape, data changes onlyA conformant bundle must use it, and scoping it to data is what keeps engine work out of a record about your company. Labels: Creation, Pull, Ingest, Query, Brief, Measure, Lint, Verify, Review, Deprecate, Migration.
One root log, not one per directoryA single timeline is what you read. A sub-bundle gets its own log the day it is lifted out.
Internal updates are timeline entries; only external observations get their own pageA page per internal update would explode the tree and break index-first navigation.
Five hard gates, queue of five1:1 prep, anything sent outward, stable Decisions and RFC outcomes, sprint goals, and design critique given to another team all require a human-reviewed page. Everything else may stay unverified as long as answers say so — and a queue longer than five is one nobody works.
Person and Stakeholder pages exist, under the §8 policyThey are the most valuable and the most sensitive part of the system. The policy, not the omission, is what makes them safe.
Sources are referenced, not copiedA local git history of company material forever is a poor price for a re-read the connector can do on demand. Verbatim only for your own notes, an explicit pin, or a metric receipt.
The middle tier is cross-check on Source pages onlyFaithfulness to a source is checkable by a second pass; judgement is not. Structural lint marks nothing, and every number goes through attestation instead.
Attested numbers: connector fetch, deterministic computeThe feed writes an immutable snapshot; the computation runs over the file and hashes both. The fetch is provenance-stamped rather than attested, and the receipt says which is which — so no script needs credentials.
RFCs and ADRs are entry points, never copiesThe canonical document stays where your team already keeps it; the page carries your summary, the options, the critique, the standards check and the outcome.
Only a short named list of feeds may pull itselfEverything else waits for your pointer. More feeds means less pointing and a faster-growing wiki, which is exactly what index-first navigation cannot survive.
Config is YAML at ~/.config/tos/config.yamlOne syntax across the system, and outside both repositories by construction, so it cannot be committed by accident. $TOS_CONFIG moves it.
One data rootA second doubles the review load. If the team wants the playbooks, they get the engine and their own root, with the exported bundle as the bridge.
Every canonical write is a scriptA format re-derived from prose drifts by the fourth Monday. The scripts also mean CLAUDE.md shrinks with each release.
Connector read-only is enforced by the harness, and verified per installA rule enforced by the thing it constrains is worth little against a source that contains an instruction — and a deny entry naming a server you do not have is silently inert.
Project is the entity the week is ranked byQueues organised by lint finding are organised for the linter. The lead's week is a walk down a priority-ordered list, which is also the report they give three different audiences.
A quiet week writes nothingThe gap in a weekly log is information, and a page that is not rewritten keeps the verification it earned. Ranking or re-pointing a project is not movement.
Pointers are optional, shape-checked, and not linksA required pointer gets filled with something plausible; a frontmatter key that satisfied the orphan check would hide a page nobody links from a section.
Objectives are phase 1, at two levels"Which objective does this advance?" is a question a project provokes in week one, long before any sprint metric exists.
Slash commands keep tos-; executables are bare verbs/tos-init exists so it does not shadow Claude Code's own /init; console scripts never had that collision, and are always written uv run <name>. After the split, tos- means "slash command" and nothing else.
Frontmatter is parsed strictlyA parser that never fails is a conformance check that never fires. The permissive fallback was deleted rather than hardened.

0 · Before you start

What you need, and the one thing to check first

On the Mac: uv (brew install uv) — it fetches the Python the engine asks for and installs its one dependency, PyYAML — plus git, Claude Code, Obsidian, and the MCP connectors you already have for Atlassian, Google Drive and web fetch. Phase 1 uses only those three, plus md for markdown in a local repository, which is read straight off disk and needs no server; Slack, Jira and Trello wait for their phases. Nothing else is installed by the engine.

The policy check — decision D5

The data root will hold summaries and short excerpts of company material (Confluence pages, Docs, later Slack threads), never copies, in a private local repository. Before Step 6 puts the first company page through it, confirm your company's policy allows that. If the answer is "in company-approved storage only", put the data root there; the config makes that a one-line change.

One thing is already decided so you do not have to: rollout.phase starts at 1, which means documents only, the eleven Phase 1 page types, and the seven commands that are built. The two locations — where the engine is cloned and where the data root sits — are yours, and neither this page nor the engine assumes anything about them: the config is the one place the data root is written down, and steps 1 and 2 put both paths in shell variables so every command below pastes and runs as it stands.

1 · The engine

Clone it wherever you like

4 minutes$TOS_ENGINE

The engine is a git repository holding instructions, the type registry, templates, the code and the docs, and no data. Its history starts at 0.5.0, the rename to TechLead OS is 0.5.1, 0.5.2 turned it into an installable package, 0.5.3 fixed the dashboard, 0.5.4 is this page, 0.6.0 gave every command the /tos- prefix, and 0.7.0 made Project the first-class entity with a weekly log and a ranked portfolio. Clone it wherever you keep code — the directory is yours to pick — then record where it landed and install it:

terminal
git clone git@github.com:RPAzevedo/TechLead-OS.git ~/code/techlead-os   # or any directory you prefer
cd ~/code/techlead-os
export TOS_ENGINE="$(git rev-parse --show-toplevel)"   # already have a checkout? cd into it and run this line alone

git log --oneline          # newest first; the top line is 0.7.0, the history starts at 0.5.0
git status --short         # nothing: the tree is clean; settings.local.json is ignored on purpose
uv --version               # brew install uv if this is missing
uv sync                    # creates .venv, installs PyYAML and the tos-* commands

That last step is the whole installation. It puts three commands behind uv run: tos-config (print the resolved config), tos-init (create the data root) and tos-lint (the deterministic half of /tos-lint). Every snippet below reaches them as uv run --directory "$TOS_ENGINE" tos-…, which runs from whatever directory you happen to be in.

Two variables, for this page only

$TOS_ENGINE is the engine checkout; $TOS_DATA, set in step 2, is the data root. The engine reads neither — it reads $TOS_CONFIG, or ~/.config/tos/config.yaml, and takes the data root from that. They exist so the commands here are the commands you actually type. A new terminal forgets them: put both export lines in ~/.zshrc if you would rather not re-run them.

Read CLAUDE.md once, top to bottom; it is the operating manual the agent loads on every run, and the guardrails in its §5 are the ones you will be relying on. Everything else in the repo is referenced from it.

2 · The config

One file, outside both repositories

5 minutes~/.config/tos/config.yaml

The config joins the engine to the data root and scopes the connectors. It lives at ~/.config/tos/config.yaml — the one fixed path on this page — is never committed, and holds no secrets: connector authentication belongs to Claude Code's MCP configuration.

terminal
mkdir -p ~/.config/tos
cp "$TOS_ENGINE"/config.example.yaml ~/.config/tos/config.yaml
open -e ~/.config/tos/config.yaml

Edit four things and leave the rest. data.root: the example ships the placeholder ~/CHANGE_ME/techlead-os-data, so replace it — the data root can go anywhere the policy check allows and need not sit next to the engine. data.actor, the actor string that will appear in every verification you make. data.timezone. And the Phase 1 connector scopes, the Confluence spaces and Google Drive folders the agent may read from. Leave rollout.phase: 1. Then tell this page the same path and check what the engine resolved:

terminal
export TOS_DATA=~/techlead-os-data      # the same path you just wrote into data.root
uv run --directory "$TOS_ENGINE" tos-config

expected output

config:   /Users/you/.config/tos/config.yaml
engine:   0.7.0 (config says 0.7)
engine root: /Users/you/code/techlead-os
data:     /Users/you/techlead-os-data  exists=False
actor:    human:you
phase:    1

The data: line and $TOS_DATA must be the same path; if they are not, one of the two edits went to the wrong place. If you ever want a second config (a team data root, later), point $TOS_CONFIG at it; the engine reads that variable first.

3 · The data root

Created by /tos-init, never by hand

2 minutescreates $TOS_DATA

Run the initialiser with the examples. It creates raw/ and wiki/ with every directory's index.md, the bundle-root index with okf_version: "0.2", log.md with its first entry, raw/inbox/pull.md, the Obsidian files, eleven example pages plus one example note, and a git repository with a first commit.

terminal
uv run --directory "$TOS_ENGINE" tos-init --with-examples

expected output (abridged)

data root: /Users/you/techlead-os-data (created)
created: raw/inbox … raw/notes … raw/pinned … raw/metrics … raw/assets
created: raw/inbox/pull.md
created: wiki/index.md … (26 index files) … wiki/log.md
vault: Home.md · .obsidian/app.json · .obsidian/community-plugins.json
example: raw/notes/example-leadership-meeting-notes.md
example: wiki/systems/example-asset-search.md … (10 pages)
git: repository initialised and first commit made

Then run the deterministic lint once, before any real content, so you know what a clean report looks like:

terminal
uv run --directory "$TOS_ENGINE" tos-lint

expected output

# Lint — 2026-08-31

11 pages · tiers {'unverified': 11, 'machine-confirmed': 0, 'human-reviewed': 0, 'changed-since-verified': 0} · conformance errors: 0

## systems (1)
- `systems/example-asset-search.md` — 1 operational standard(s) unticked

The one finding is intended: the example System page has an unticked standard, so you can see what lint says about one. Eleven pages, all unverified: nothing is trusted until you say so.

4 · Obsidian

Open the data root as the vault

5 minutesplugin: Dataview

Obsidian → Open folder as vault → your data root. echo "$TOS_DATA" prints the path; ⌘⇧G in the file dialog takes a typed one. Not the engine: the vault is the data. The settings /tos-init installed are already in place: markdown links rather than wikilinks, relative link paths, attachments in raw/assets/, so anything you write by hand in a note will link the way the agent's pages do.

Install Dataview: Settings → Community plugins → turn off Restricted mode → Browse → Dataview → Install → Enable. Then open Home.md. Three of its nine queries have something to show on day one: Portfolio lists the example project, Unverified, newest first lists nine pages — it leaves out the weekly Review and the active project, which answers for its own trust in the portfolio — and Open questions lists the example Question. The other six are empty, and that is the right answer rather than a fault: Systems due for review looks fourteen days ahead and the example System does not expire for ninety, RFCs stuck in draft wants a draft a fortnight old, and nothing has yet expired, been verified, or passed a checkpoint. Home.md is an alarm panel; on a fresh vault almost all of it is quiet. If every table is empty, the first one included, Dataview is not enabled; if they show errors, see §10.

Open wiki/index.md and follow a link or two. That top-down path, root index → directory index → page, is the one the agent takes for every query.

5 · Claude Code and connectors

Start it in the engine, grant it the data

15 minutesconnectors: atlassian · google-drive · fetch

Claude Code loads CLAUDE.md from the directory it starts in, so the session always starts in the engine. The data root is a separate directory, and Claude Code will not write outside its working directory unless told. Say so on the command line and you are done:

terminal
cd "$TOS_ENGINE" && claude --add-dir "$TOS_DATA"

To stop repeating the flag, grant the directory once in .claude/settings.local.json. The engine ignores that file rather than shipping it — it is per-machine, and your data root is not necessarily anyone else's — so it does not exist until you create it:

engine/.claude/settings.local.json
{
  "permissions": {
    "additionalDirectories": ["/Users/you/techlead-os-data"]
  }
}

Give it the absolute path to your own data root — the file is JSON, which expands neither ~ nor $TOS_DATA. echo "$TOS_DATA" prints exactly what to paste. Then the session starts plainly:

terminal
cd "$TOS_ENGINE" && claude

Two checks inside the session. First, that the manual loaded and the config resolved:

claude
> what is the data root, which phase are we in, and which connectors may you use?

expected answer, in substance

The data root is the path you set in data.root (read from ~/.config/tos/config.yaml); rollout phase 1; the connectors enabled for this phase are confluence, gdocs, web and md, within the scopes in the config. It should also say that it never writes the config and never writes outside raw/ and wiki/.

Second, the connectors. Each names two separate things: provider: mcp:<kind>, which selects the write-tool vocabulary in schema/connector-writes.yaml, and mcp_server, which must equal the server name as Claude Code lists it — one name or several, since Jira and Confluence are often different servers:

terminal
claude mcp list       # expect atlassian, google-drive, fetch (or whatever you named them)

If your servers have different names, change the config's mcp_server values to match rather than renaming the servers, and leave provider alone. Then run uv run tos-deny, which reports which of those servers' write tools are not yet denied and adds them with --write. Then confirm the scope check works by pointing at something outside it:

claude
> /tos-pull https://example.atlassian.net/wiki/spaces/NOTINSCOPE/pages/1/Test

expected answer, in substance

A refusal that names the setting: the space is not in connectors.confluence.scope.spaces, so nothing was fetched, and which line in the config would allow it. That refusal is guardrail 12 working; you want to have seen it once.

Finally, /tos-init from inside the session does nothing new on an existing data root; it re-installs the vault files and reports any drift between the engine version and the config. Run it once so you know what the no-op looks like.

6 · The first loop

Five sources, three questions, one lint, the same afternoon

45 minutesthe afternoon of Phase 0

The design's Phase 0 ends with five sources you already know you need, so the first /tos-query has something real to find. Pick these five, or the nearest equivalents you have:

  1. The Lead Engineer role description — a markdown file; drop it into raw/inbox/.
  2. The System Owner expectations page — Confluence; a pointer.
  3. The PDLC page — Confluence; a pointer.
  4. One RFC you are currently reviewing — a Doc or Confluence page; a pointer, plus a note with your review comments.
  5. One runbook for a system you own — Confluence; a pointer.
terminal — put the pointers in place
cp ~/Downloads/leadengineer.md "$TOS_DATA"/raw/inbox/2026-08-31-lead-engineer-role.md
cat >> "$TOS_DATA"/raw/inbox/pull.md <<'EOF'
https://<your-site>.atlassian.net/wiki/spaces/ENG/pages/…/System+Owner+expectations
https://<your-site>.atlassian.net/wiki/spaces/PDLC/pages/…/Product+Development+Lifecycle
https://docs.google.com/document/d/…/edit
https://<your-site>.atlassian.net/wiki/spaces/ENG/pages/…/Asset+search+runbook
EOF
claude — in this order
> /tos-ingest                 # the role description becomes a Source page and, probably, a few Concept pages
> /tos-pull                   # the four pointers; a Source page each; the runbook creates or updates a System page; the RFC gets its entry point
> /tos-query which systems do I own, and what do the System Owner expectations require of each?
> /tos-query what does the RFC I am reviewing change for the systems we own, and what does it not address?
> /tos-query what does the PDLC say a lead engineer is responsible for at each stage?
> /tos-lint
> /tos-verify --queue         # verify what you would quote; skip the rest

What to look for in the answers: every page cited with a tier and a date; the RFC page unverified and your review notes marked as yours; the System page's Operational standards ticked or unticked with footnotes; nothing stated without a source. If an answer states something with no citation, that is an engine bug; note it for the weekly review's Engine proposals. What to look for in the data root afterwards: the four pointer lines gone from pull.md, your note moved to raw/notes/ untouched, under today's date in wiki/log.md an Ingest for the note and a Pull with its Ingest for each of the four pointers, each of those its own commit in git log, and nothing at all under raw/pinned/, because you did not ask for a pin.

The other three commands are quieter than that makes them sound, and deliberately so — only a change to the wiki earns a line. A /tos-query logs and commits when the answer was reusable enough to file as a Synthesis; a query that merely answers you leaves no trace, so do not expect three lines for three questions. /tos-lint without --fix writes its findings into this week's Review page and neither logs nor commits, so expect an uncommitted change in the data root after it. /tos-verify --queue logs and commits once per page you said yes to, and nothing for the ones you skipped.

Then remove the examples, so the wiki is yours: uv run --directory "$TOS_ENGINE" tos-init --remove-examples. Keep them a few more days if you want a second reference for what a good page looks like.

7 · The first fortnight

The acceptance test

The design's advice, Karpathy's advice, is to let use change the schema rather than another review. Two weeks with a small, deliberate test is enough to know whether the loop holds and what the engine's first changelog entries should be.

WhenYou doYou should see
Day 1Steps 1–6.Five Source pages, three cited answers, a clean lint apart from what you left unticked.
Days 2–5, end of dayNotes into raw/inbox/, pointers into pull.md; /tos-ingest then /tos-pull. Two /tos-query during the day, whenever you would have searched.Each day's log entries; pages accumulating under the domains you actually work in; answers that name their tiers.
Monday (day 8)/tos-weekly; answer the page inline in Obsidian; /tos-weekly --apply.A verify queue of five, a re-pull queue if any Doc changed, expiring pages with a choice each, RFCs awaiting you, systems due, questions; one log line per action after apply.
Days 9–12Same daily rhythm. Before any meeting about a project, the S3 brief from the scenarios page — which is a /tos-query and works in Phase 1, not the Phase 3 /tos-brief — then /tos-verify --queue.The first time a brief flags something unverified that you would otherwise have quoted.
Monday (day 15)Second /tos-weekly. Then the verdict: read the two review pages and the Engine proposals sections.At least two or three proposals worth applying — a heading that keeps being needed, a type that was never used, a guardrail that got in the way. Those become the engine's next release.

Ten queries, one lint per week, two Monday reviews, at most ten verifications. Do not add Slack, Jira or the sprint tick during the fortnight, however tempting; they are Phases 2 and 3, and the point of the test is to judge the loop on documents alone.

8 · What working looks like

Five signs, after two weeks

The design's eight-week criteria, scaled to Phase 1. If four of the five hold, the loop holds. If fewer do, the fix is usually one of the four habits (scenarios page, §10), not the engine.

  • Monday came off the page. Most of what you did on the second Monday was answer the review page, not assemble it.
  • Every owned system has a page you have verified, with its standards ticked or unticked on evidence.
  • The verify queue never exceeded five, and you never quoted an unverified page outward without knowing it.
  • The RFC you reviewed has an entry point whose Outcome matches what happened, and the drift check noticed when the Doc changed.
  • The engine has changelog entries, because an engine that never changed is one nobody used.

9 · Later phases

Enabling what is designed but not yet built

The commands for later phases exist and refuse to run until rollout.phase reaches them, so nothing is improvised. Each phase is two weeks in the design, and each needs engine work before the config changes:

Phase 2
Jira · sprint tick

Build first: src/tos/metrics/ (executor, attester, a sprint-completion script), the /tos-sprint and /tos-measure procedures, the sprint-report feed. Then: Jira scope in the config, the feed uncommented, rollout.phase: 2. Goal: a sprint review whose numbers carry receipts.

Phase 3
team · Slack · /tos-brief

Build first: the /tos-brief procedure, the Slack pull procedure (named channels, digests, "awaiting you"), the comms-due and 1:1 sections of the weekly. Then: Slack channels in scope, the people policy re-read, rollout.phase: 3. Goal: 1:1 prep in two minutes; the first brief sent from the wiki.

Phase 4
vision · learning · radar

Build first: the /tos-retro procedure, the radar overview synthesis, Learning Path and Drill handling in the weekly. Then: Trello (personal) if wanted, rollout.phase: 4. Goal: a vision you can socialise, with the signals it watches attached.

Each phase's build is a change to the engine, recorded in CHANGELOG.md; enabling it is a change to your config; neither touches wiki/log.md unless a migration of existing pages follows, and then it is logged as one.

10 · Troubleshooting

When a step does not look like its expected output

You seeCauseDo
config not found: …No config at the default path and $TOS_CONFIG unset.Step 2. The message names the file to copy.
config at … has no data.rootThe YAML is malformed or data: was removed.Compare with config.example.yaml; indentation is two spaces.
The agent says the data root does not existStep 3 not run, or data.root points elsewhere.uv run --directory "$TOS_ENGINE" tos-config, then /tos-init.
command not found: tos-lintThe engine is not installed.cd "$TOS_ENGINE" && uv sync, and invoke through uv run.

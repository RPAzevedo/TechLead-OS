0 · Before you start

What you need, and the one thing to check first

On the Mac: Python 3.9 or later (the scripts are standard library only; PyYAML is used if present and not required), git, Claude Code, Obsidian, and the MCP connectors you already have for Atlassian, Google Drive and web fetch. Phase 1 uses only those three; Slack, Jira and Trello wait for their phases. Nothing else is installed by the engine.

The policy check — decision D5

The data root will hold summaries and short excerpts of company material (Confluence pages, Docs, later Slack threads), never copies, in a private local repository. Before Step 6 puts the first company page through it, confirm your company's policy allows that. If the answer is "in company-approved storage only", put the data root there; the config makes that a one-line change.

Two things are already decided so you do not have to: the data root defaults to ~/Code/POS/data next to the engine, and rollout.phase starts at 1, which means documents only, the ten Phase 1 page types, and the seven commands that are built.

1 · The engine

It is already on your Mac

2 minutes~/Code/POS/engine

The engine repository was created under ~/Code/POS/engine; its history starts at 0.5.0 and the rename to TechLead OS is 0.5.1. It holds instructions, the type registry, templates, scripts and the docs, and no data. Confirm it is what you expect:

terminal
cd ~/Code/POS/engine
git log --oneline          # the newest commit is the rename to TechLead OS (0.5.1); the first is commonplace-engine 0.5.0
git status --short         # nothing: the tree is clean; settings.local.json is ignored on purpose
python3 --version          # 3.9 or later

Read CLAUDE.md once, top to bottom; it is the operating manual the agent loads on every run, and the guardrails in its §5 are the ones you will be relying on. Everything else in the repo is referenced from it.

2 · The config

One file, outside both repositories

5 minutes~/.config/tos/config.yaml

The config joins the engine to the data root and scopes the connectors. It lives at ~/.config/tos/config.yaml, is never committed, and holds no secrets: connector authentication belongs to Claude Code's MCP configuration.

terminal
mkdir -p ~/.config/tos
cp ~/Code/POS/engine/config.example.yaml ~/.config/tos/config.yaml
open -e ~/.config/tos/config.yaml

Edit four things and leave the rest: data.root if you want the data somewhere other than ~/Code/POS/data (the policy check may decide this); data.actor, the actor string that will appear in every verification you make; data.timezone; and the Phase 1 connector scopes, the Confluence spaces and Google Drive folders the agent may read from. Leave rollout.phase: 1. Then check what the engine resolved:

terminal
cd ~/Code/POS/engine && python3 scripts/tos_common.py --show

expected output

config:   /Users/raf/.config/tos/config.yaml
engine:   0.5.1 (config says 0.5)
data:     /Users/raf/Code/POS/data  exists=False
actor:    human:rafael
phase:    1
yaml:     PyYAML   # or "built-in subset parser" — both are fine

If you ever want a second config (a team data root, later), point $TOS_CONFIG at it; the engine reads that variable first.

3 · The data root

Created by /init, never by hand

2 minutescreates ~/Code/POS/data

Run the initialiser with the examples. It creates raw/ and wiki/ with every directory's index.md, the bundle-root index with okf_version: "0.2", log.md with its first entry, raw/inbox/pull.md, the Obsidian files, ten example pages plus one example note, and a git repository with a first commit.

terminal
python3 scripts/init.py --with-examples

expected output (abridged)

Then run the deterministic lint once, before any real content, so you know what a clean report looks like:

terminal

The one finding is intended: the example System page has an unticked standard, so you can see what lint says about one. Ten pages, all unverified: nothing is trusted until you say so.

4 · Obsidian

Open the data root as the vault

5 minutesplugin: Dataview

Obsidian → Open folder as vault → ~/Code/POS/data. Not the engine: the vault is the data. The settings /init installed are already in place: markdown links rather than wikilinks, relative link paths, attachments in raw/assets/, so anything you write by hand in a note will link the way the agent's pages do.

Install Dataview: Settings → Community plugins → turn off Restricted mode → Browse → Dataview → Install → Enable. Then open Home.md. Its eight queries should show the example pages: ten unverified pages in the first table, the System page under Systems due for review with its date ninety days out, the example RFC nowhere yet (it is not two weeks old), the example Question under Open questions. If the tables are empty, Dataview is not enabled; if they show errors, see §10.

Open wiki/index.md and follow a link or two. That top-down path, root index → directory index → page, is the one the agent takes for every query.

5 · Claude Code and connectors

Start it in the engine, grant it the data

15 minutesconnectors: atlassian · google-drive · fetch

Claude Code loads CLAUDE.md from the directory it starts in, so the session always starts in the engine. The data root is a separate directory, and Claude Code will not write outside its working directory unless told: .claude/settings.local.json already grants /Users/raf/Code/POS/data as an additional working directory. If your data root is elsewhere, edit that file, or start with claude --add-dir <data.root>.

terminal
cd ~/Code/POS/engine && claude

Two checks inside the session. First, that the manual loaded and the config resolved:

claude
> what is the data root, which phase are we in, and which connectors may you use?

expected answer, in substance

The data root is /Users/raf/Code/POS/data (from ~/.config/tos/config.yaml); rollout phase 1; the connectors enabled for this phase are confluence, gdocs, web and md, within the scopes in the config. It should also say that it never writes the config and never writes outside raw/ and wiki/.

Second, the connectors. The config names each one as provider: mcp:<name>, and the part after mcp: must equal the server name as Claude Code lists it:

terminal
claude mcp list       # expect atlassian, google-drive, fetch (or whatever you named them)

If your servers have different names, change the config's provider values to match rather than renaming the servers. Then confirm the scope check works by pointing at something outside it:

claude
> /pull https://example.atlassian.net/wiki/spaces/NOTINSCOPE/pages/1/Test

expected answer, in substance

A refusal that names the setting: the space is not in connectors.confluence.scope.spaces, so nothing was fetched, and which line in the config would allow it. That refusal is guardrail 12 working; you want to have seen it once.

Finally, /init from inside the session does nothing new on an existing data root; it re-installs the vault files and reports any drift between the engine version and the config. Run it once so you know what the no-op looks like.

6 · The first loop

Five sources, three questions, one lint, the same afternoon

45 minutesthe afternoon of Phase 0

The design's Phase 0 ends with five sources you already know you need, so the first /query has something real to find. Pick these five, or the nearest equivalents you have:

  1. The Lead Engineer role description — a markdown file; drop it into raw/inbox/.
  2. The System Owner expectations page — Confluence; a pointer.
  3. The PDLC page — Confluence; a pointer.
  4. One RFC you are currently reviewing — a Doc or Confluence page; a pointer, plus a note with your review comments.
  5. One runbook for a system you own — Confluence; a pointer.
terminal — put the pointers in place
cp ~/Downloads/leadengineer.md ~/Code/POS/data/raw/inbox/2026-08-31-lead-engineer-role.md
cat >> ~/Code/POS/data/raw/inbox/pull.md <<'EOF'
https://<your-site>.atlassian.net/wiki/spaces/ENG/pages/…/System+Owner+expectations
https://<your-site>.atlassian.net/wiki/spaces/PDLC/pages/…/Product+Development+Lifecycle
https://docs.google.com/document/d/…/edit
https://<your-site>.atlassian.net/wiki/spaces/ENG/pages/…/Asset+search+runbook
EOF
claude — in this order
> /ingest                 # the role description becomes a Source page and, probably, a few Concept pages
> /pull                   # the four pointers; a Source page each; the runbook creates or updates a System page; the RFC gets its entry point
> /query which systems do I own, and what do the System Owner expectations require of each?
> /query what does the RFC I am reviewing change for the systems we own, and what does it not address?
> /query what does the PDLC say a lead engineer is responsible for at each stage?
> /lint
> /verify --queue         # verify what you would quote; skip the rest

What to look for in the answers: every page cited with a tier and a date; the RFC page unverified and your review notes marked as yours; the System page's Operational standards ticked or unticked with footnotes; nothing stated without a source. If an answer states something with no citation, that is an engine bug; note it for the weekly review's Engine proposals. What to look for in the data root afterwards: the four pointer lines gone from pull.md, your note moved to raw/notes/ untouched, five new lines under today's date in wiki/log.md, one commit per operation in git log, and nothing at all under raw/pinned/, because you did not ask for a pin.

Then remove the examples, so the wiki is yours: python3 scripts/init.py --remove-examples. Keep them a few more days if you want a second reference for what a good page looks like.

7 · The first fortnight

The acceptance test

The design's advice, Karpathy's advice, is to let use change the schema rather than another review. Two weeks with a small, deliberate test is enough to know whether the loop holds and what the engine's first changelog entries should be.

WhenYou doYou should see
Day 1Steps 1–6.Five Source pages, three cited answers, a clean lint apart from what you left unticked.
Days 2–5, end of dayNotes into raw/inbox/, pointers into pull.md; /ingest then /pull. Two /query during the day, whenever you would have searched.Each day's log entries; pages accumulating under the domains you actually work in; answers that name their tiers.
Monday (day 8)/weekly; answer the page inline in Obsidian; /weekly --apply.A verify queue of five, a re-pull queue if any Doc changed, expiring pages with a choice each, RFCs awaiting you, systems due, questions; one log line per action after apply.
Days 9–12Same daily rhythm. Before any meeting about a project, the S3 brief from the scenarios page, then /verify --queue.The first time a brief flags something unverified that you would otherwise have quoted.
Monday (day 15)Second /weekly. Then the verdict: read the two review pages and the Engine proposals sections.At least two or three proposals worth applying — a heading that keeps being needed, a type that was never used, a guardrail that got in the way. Those become the engine's 0.5.1.

Ten queries, one lint per week, two Monday reviews, at most ten verifications. Do not add Slack, Jira or the sprint tick during the fortnight, however tempting; they are Phases 2 and 3, and the point of the test is to judge the loop on documents alone.

8 · What working looks like

Five signs, after two weeks

The design's eight-week criteria, scaled to Phase 1. If four of the five hold, the loop holds. If fewer do, the fix is usually one of the four habits (scenarios page, §10), not the engine.

  • Monday came off the page. Most of what you did on the second Monday was answer the review page, not assemble it.
  • Every owned system has a page you have verified, with its standards ticked or unticked on evidence.
  • The verify queue never exceeded five, and you never quoted an unverified page outward without knowing it.
  • The RFC you reviewed has an entry point whose Outcome matches what happened, and the drift check noticed when the Doc changed.
  • The engine has changelog entries, because an engine that never changed is one nobody used.

9 · Later phases

Enabling what is designed but not yet built

The commands for later phases exist and refuse to run until rollout.phase reaches them, so nothing is improvised. Each phase is two weeks in the design, and each needs engine work before the config changes:

Phase 2
Jira · sprint tick

Build first: scripts/metrics/ (executor, attester, a sprint-completion script), the /sprint and /measure procedures, the sprint-report feed. Then: Jira scope in the config, the feed uncommented, rollout.phase: 2. Goal: a sprint review whose numbers carry receipts.

Phase 3
team · Slack · /brief

Build first: the /brief procedure, the Slack pull procedure (named channels, digests, "awaiting you"), the comms-due and 1:1 sections of the weekly. Then: Slack channels in scope, the people policy re-read, rollout.phase: 3. Goal: 1:1 prep in two minutes; the first brief sent from the wiki.

Phase 4
vision · learning · radar

Build first: the /retro procedure, the radar overview synthesis, Learning Path and Drill handling in the weekly. Then: Trello (personal) if wanted, rollout.phase: 4. Goal: a vision you can socialise, with the signals it watches attached.

Each phase's build is a change to the engine, recorded in CHANGELOG.md; enabling it is a change to your config; neither touches wiki/log.md unless a migration of existing pages follows, and then it is logged as one.
